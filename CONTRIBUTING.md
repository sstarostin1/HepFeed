# CONTRIBUTING.md — как вести разработку

## Общая модель

Проект публичный; разработка идёт через ветки и pull request'ы. Прямые коммиты в `main` не поощряются (для solo-разработки допустимы, но история должна оставаться читаемой).

- **`main`** — всегда рабочее состояние; форс-пуш запрещён.
- Секреты никогда не попадают в коммиты — см. [docs/SECURITY_NOTE.md](docs/SECURITY_NOTE.md). В репозитории подключён pre-commit hook `gitleaks`.

## Ветки

| Префикс | Назначение |
|---|---|
| `feat/<кратко>` | новая функциональность |
| `fix/<кратко>` | исправления |
| `docs/<кратко>` | документация |
| `chore/<кратко>` | инфраструктура, зависимости, CI |

## Conventional Commits

```
<type>(<scope>): <краткое описание>
```

- Типы: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `ci`.
- Описание — в инфинитиве, строчными буквами, без точки в конце.
- Пример: `feat(ingestion): add arxiv atom poller`

## Pull request'ы

1. Заполняется шаблон `.github/PULL_REQUEST_TEMPLATE.md`.
2. Одна логическая тема на PR; мелкие PR предпочтительнее крупных.
3. Перед PR — линтер и тесты зелёные (появятся вместе с кодом).
4. Изменения концепции или спецификации источников — через PR в `docs/`, чтобы история решений сохранялась.

## Код

- Python 3.11+, стиль — **ruff** (lint + format), type hints обязательны.
- Тесты — **pytest**, каталог `tests/`; приоритет — дедупликация и фильтрация.
- Конфигурация — только через переменные окружения (шаблон — [.env.example](.env.example)).

## Секреты

- Никогда не коммитить: токены Telegram, API-ключи, пароли БД.
- Случайно закоммитили? Считать скомпрометированным: ротация → чистка истории → см. [docs/SECURITY_NOTE.md](docs/SECURITY_NOTE.md).
